# 跨项目 AI 开发工作台与完整工作流：正式实施方案

**版本：** v1.0  
**日期：** 2026-11-13（Asia/Shanghai；2026-11-12 开始编制）  
**文档性质：** 正式方案与实施、验收基线；不是实现完成或部署成功的声明。  
**批准背景：** 用户已同意统一工作台、专门交互助手和独立人工操作中心的总体设计，并要求长期跨项目使用、方便接入新项目、在工作台配置包括交互助手在内的模型角色。  
**本次实际动作：** 只读核对现有实现和相关资料，编制本方案；未部署工作台、未切换模型、未修改全局规范、未接入业务项目、未触发工作流模型消费。

---

## 1. 执行结论

建设一套**独立安装、长期维护、跨项目复用的本地 AI 开发工作台**。工作台是统一的人机入口，专门助手负责交互与起草，现有确定性控制面继续负责执行，GitHub/Git/Obsidian 保留各自的权威职责。

最终产品不是“给练习库套一个界面”，也不是重新开发通用 Agent 编排器，而是：

**单窗口工作台 + WorkbenchAssistant + 类型化操作代理 + 人类授权服务 + 项目化执行控制面 + 原生工具/技术栈适配器。**

必须同时达到以下结果：

1. 项目日常工作流的人类操作在工作台完成，不要求用户手敲终端命令。
2. 新建项目和已有项目均可通过向导接入；已支持的技术栈不要求用户修改平台源码。
3. 平台不依赖练习库名称、绝对路径、专用测试或固定 AO 项目标识。
4. WorkbenchAssistant、Director、Planner、Builder、Reviewer、Knowledge 使用统一且可视化的模型配置体系。
5. 人类批准、最终合并和知识接受仍由人类决定；新增助手不能代行。
6. 真正贯通需求、任务、批准、执行、验证、审查、PR/CI、合并、完成状态与知识审核，不以界面展示代替完整闭环。
7. 保留失败现场、预算、检查点和证据，支持断线、重启、升级和恢复。

“跨项目”不等于“所有操作系统和任意工具链已经验证”。首个正式运行环境为现有 Linux 主机；其他运行环境按适配合同分别验证，不伪装为已支持。

## 2. 授权范围与不可变边界

### 2.1 本方案涵盖

- 操作台、交互助手、项目登记、任务准备、角色模型配置、运行控制、可信人类操作入口。
- GitHub Issue/PR/Projects 交互、服务器门禁核对、人工合并后的安全收口。
- 技术栈适配、冻结验收、复杂任务阶段队列、知识审核和维护操作。
- 独立平台发布、版本化配置、恢复、备份、升级与回滚。

### 2.2 不由本次编制方案自动授权

- 修改全局 Codex 规则、全局默认模型、登录或系统权限。
- 直接修改或接入 FishMuse、DevFlow 等已有业务仓库。
- 新建公开远端、改变仓库可见性、上传私有代码、删除仓库或重写历史。
- 生产部署、对外发布、购买套餐、增加费用或扩大当前 1 USD 消费授权。
- 修改、删除或搬移任何既有正式 Obsidian 笔记。

用户在后续工作台中选择项目或模型，只授权所展示的具体对象和操作，不产生无限授权。

### 2.3 原规范的处理

保留现有全局规范不变。新增 Web 人类入口、依赖与知识人控服务，需要在平台自己的项目级规范、规格和 ADR 中明确：

- 将“独立交互终端批准”扩展为“独立终端或通过认证的可信人类 Web 入口”。
- CLI 保留；不伪造 TTY，不脚本代输 APPROVE/DRAFT。
- 新 Web 层依赖单独声明，不暗中违反现有连接层“标准库、不引入额外依赖”的限制。
- 知识正式审核由单独的人控服务处理，不扩大 Assistant 或 Draft Writer 的权限。

## 5. 平台结构与技术路线

### 5.1 独立平台，而不是业务仓库内的脚本集合

建立独立的平台源码和发行包，名称拟为 `ai-workflow-workbench`。仓库位置、远端与可见性在实施时明确确认，不因本方案自动创建或公开。

- `workflow-core`：提取并演进现有 Python 控制面，保持薄连接层。
- `workbench-server`：本地 API、认证、人类操作、助手会话和后台作业接口。
- `workbench-web`：单窗口前端。
- `adapters`：Harness、Provider、AO、GitHub、技术栈与运行器适配。
- `project-presets`：版本化接入模板和迁移定义。
- `operator-launcher`：桌面入口、服务状态、打开工作台与受控重启。

业务项目不复制平台实现、starter 测试、运行数据库或凭据。练习库保留为验收样本，不再作为所有项目的运行根目录。

### 5.2 技术选型

拟采用 Python 控制核心、FastAPI/Uvicorn Web 服务、React/TypeScript/Vite 前端与 SQLite 私有状态。此为本方案的工程选型，不是这些依赖已安装或已批准写入旧项目的声明。

- Python core 与 Web 依赖边界分开；新依赖经平台项目规范/ADR和锁文件审阅。
- 前端编译为本地静态资源，不运行开发服务器承担长期服务，不依赖第三方 CDN。
- 服务只监听本机回环地址；生产启动不启用热重载。
- SQLite 用于本机单操作者控制与审计；不把它宣传为多租户云平台。
- Vite 只负责构建平台 UI，不改变 FishMuse、DevFlow 或其他项目的工具链。

选型依据见 [S6]、[S7]。不使用 `python -m http.server` 充当长期审批后端，见 [S8]。

### 5.3 核心服务

| 服务 | 职责 |
|---|---|
| ProjectRegistry/ProjectContext | 登记项目、稳定身份、目录/远端/规则与运行器绑定 |
| ConfigurationService | 模型、角色、Tier、模式、价格和策略的版本化解析 |
| AssistantService | 对话、上下文选择、文本产物、类型化动作提案 |
| ActionBroker | 参数、范围、身份、前置状态、幂等与固定动作执行 |
| HumanActionService | 仅接收真实操作员关键确认，不对模型暴露 |
| Dispatcher | 保留模型阶段、候选、验证、审查、发布与恢复的唯一执行控制权 |
| JobSupervisor | 后台进程归属、租约、取消、重连、状态协调 |
| EvidenceService | 冻结输入、验证记录、模型元数据、脱敏与证据查询 |
| KnowledgeReviewService | 相关笔记查重、人类审核、精确的人控知识操作 |

## 6. 单窗口界面与人工动作覆盖

### 6.1 布局

- 顶部：项目、仓库、模式、基准、配置版本、预算和连接状态。
- 左侧：项目、任务、运行、待我处理、知识、模型与设置、维护。
- 中央：当前任务说明、执行合同、计划、diff、测试/CI、知识正文。
- 右侧：常驻 WorkbenchAssistant，始终标明当前项目和选中对象。
- 独立操作区：可信批准卡、合并卡、配置发布卡、知识确认卡。

状态更新来自真实工具和账本；助手说“成功”不能改变执行状态。

### 6.2 完整覆盖表

| 人工事项 | 工作台实现 |

| 新建/接入项目 | 向导、变更预览、规则检测、接入 PR、就绪报告 |
| 密钥和账号 | 独立安全表单、认证状态、受控官方授权跳转 |
| 模型与角色 | Profile 管理、六个模型角色分配、兼容性、费用、版本/回滚 |
| 需求澄清 | 助手对话、问题清单、范围和不做事项 |
| 任务与阶段 | 可编辑说明、白名单合同、依赖图、Issue 发布预览 |
| 验收准备 | 检测缺口、起草配置、独立审阅与冻结，不伪造已有测试 |
| 任务批准 | 展示准确执行主体、版本、路径、模式、预算和有效期 |
| 高风险计划 | 单独展示和批准具体 plan digest |
| 启动与异常 | 启动、停止接单、取消、检查恢复条件、脱敏诊断 |

第三方密码、MFA、设备授权、CAPTCHA、账单或套餐处理可受控跳转到官方页面并返回原步骤，不能保证强行嵌入单一页面，也不代收验证码或密码。

## 7. WorkbenchAssistant 角色合同

### 7.1 定位和激活

新增第八种职责 `WorkbenchAssistant`，属于前台交互层；模型角色共六个。它不加入每个 Issue 必跑的固定流水线。

由用户消息、起草/解释按钮、用户明确允许的诊断动作激活。界面刷新、轮询和普通状态变化不得隐式调用模型。

### 7.2 输入与记忆

输入包括当前项目规则、已确认目标、选中的任务/运行/PR、必要源码和脱敏证据、用户选择的相关知识。

- 会话按项目隔离，保存草稿版本、引用和动作回执。
- 长对话由控制面保留原始私有记录并进行有来源的上下文裁剪；摘要不替代正式规格。
- 不默认继承当前 Codex 聊天，不自动读取全仓、整个 Vault 或其他项目对话。
- 正式知识只作支持性上下文；pending/rejected 明确标未验证。
- 附件、Issue、代码、日志、网页中的指令性文字均不能提升权限。

### 7.3 输出与能力

输出分为解释文本、澄清问题、可编辑文稿、结构化任务/阶段草稿和类型化操作提案。

可起草任务说明、规格、ADR、验收计划、PR描述、故障说明等；正式写入 Git 或发布 GitHub 必须经过对应操作和授权。产品代码实施仍交由 Builder；助手不另建可写开发会话争抢候选。

查询和已授权普通运行操作可按明确用户请求执行。批准、合并、知识接受、模型/权限政策发布等只能提交到人工操作中心。

### 7.4 原生调用与上限

会话由平台维护，再调用所选原生 Harness；不假称当前已有原生长期聊天后端。每轮设上下文、输出、时间和工具轮次上限；不无限后台自循环。

助手可在一次交互中请求多次受控查询，结果由 Broker 返回。模型只产生结构化请求，不直接得到 shell、GitHub写凭据、批准密钥或人类浏览器会话。

## 8. 统一模型配置体系（必须实现）

### 8.1 可配置对象

工作台支持六个模型角色：`WorkbenchAssistant`、`Director`、`Planner`、`Builder`、`Reviewer`、`Knowledge`。

`Router`、`Dispatcher` 保持确定性职责：界面可配置其路由/并发/动作策略，但不显示虚假的模型选择器。

**Role、Tier、Harness、Provider、Model、Auth 是不同概念，不能混为一个“模型名称”。**

### 8.2 Profile 合同

每个 Profile 至少包含：

- 稳定 ID、名称、不可变修订号；
- Harness 与适配器版本；Provider、协议、受信 endpoint 标识；
- 请求模型 ID/别名与可用账号范围；
- 私有凭据引用及版本，不保存 Key 原值；
- 上下文、最大输出、支持的推理/采样参数；
- 结构化输出、工具和隔离能力合同；
- 价格单位、币种、额外计费项、官方来源和核实日期；
- production/validation 适用范围；
- 支持状态及实际验证证据。

模型名称可从供应商目录发现，但目录存在不等于账号可用或本平台兼容。普通设置页不接受模型生成的任意 endpoint、可执行路径或命令。

### 8.3 配置层级与模式

解析顺序：**平台强制安全约束 → 工作台全局模板 → 项目绑定/覆盖 → 角色与 Tier 绑定 → 获批单次选择 → 不可变执行快照。**

- 工作台全局模板是平台自己的配置，不是 `$HOME/.codex/config.toml`。
- 先选 production/validation，再在该模式中解析；两者不互相静默回退。
- 新项目可选择并固定模板版本，不逐角色重填。
- 模板更新展示受影响项目，由用户选择升级；不自动改已接入项目。
- 每角色支持“继承”和“本项目覆盖”，始终显示最终生效值及来源。
- 角色可按 Tier 指定不同 Profile，并显示失败升级路线；临时选择同样受风险和费用政策限制。
- Knowledge 不再永久锁死某个厂商，用户可经相同受控配置机制更换；独立会话、最小上下文和无 Vault 写权限不变。

### 8.4 设置页与操作流程

设置页包含 Profiles、角色分配、Tier/升级路线、账号凭据、兼容验证、费用与预算、配置历史。

流程为：**编辑草稿 → 静态校验 → 展示有效配置及来源 → 展示影响范围/费用差异 → 本人确认发布 → 新修订生效。**

“保存配置”不得产生模型请求。“测试连接/真实调用”必须另行标识可能费用、经过预算检查并保存证据。

如选择“继承当前 Codex 模型”，批准时解析必要的非敏感有效设置形成快照，不能仅冻结一个 `null`，随后任由全局设置漂移。工作台修改模型只影响工作流专属配置或单次调用参数，不静默改用户全局模型和登录。Codex 单次参数覆盖能力见 [S5]。

### 8.5 在途变更与回滚

- 已运行任务固定引用已批准配置，不热切换。
- 保存配置草稿不影响任务；发布新修订默认用于未来派发，并使受影响、尚未执行的旧批准失效。
- 如要将新配置应用到现有运行，应安全停止，重新准备、批准和验证，不能沿用旧产物/审查。
- 关键安全策略或凭据被撤销时，阻止后续阶段，不能以旧快照继续越权。
- 助手切模型时，当前回复先结束或取消，下一轮用新配置，并标记会话段与模型版本。
- 回滚选择旧配置内容生成新修订；不改旧快照，不复活过期批准，不倒退账本。

### 8.6 兼容性和风险下限

只开放已实现适配的 Harness/Provider/Model/参数组合，状态区分“已验证”“仅 validation 验证”“已配置未验证”“不兼容”。

- Codex：保留既有登录；参数和支持模型依本机及官方合同核验。
- Claude Code：Anthropic 正式路径与 DeepSeek 测试兼容路径分别核验。
- OpenCode：移除当前固定模型硬编码，按受控 Profile 生成配置。
- 新 Provider/Harness：先补充协议、隔离、计量和回归，不是改名称即支持。

Tier 不是价格或模型智商证明。将便宜模型命名为 T1，不会自动获得高风险适用资格；更改资格策略需要显式审阅，且不取消计划批准、路径和工具约束。

### 8.7 调度证据

每次调用分别记录：角色、Tier、Profile修订、Harness/适配器版本、请求模型、供应商报告值、可核实实际模型及来源、原生会话 ID、用量与计费状态。

实际模型无法证实则保留 `null`，不能用设置页的选择值填充“实际模型”。更换配置后执行快照、缓存和批准必须正确隔离。

## 9. 新项目与已有项目接入

### 9.1 新建项目：向导式完成

入口“新建项目”：选择名称和目录 → 选择技术栈模板 → 选择已有模型模板 → 预览文件/远端/权限/费用 → 明确确认 → 初始化 → 环境诊断 → 门禁验收 → 登记可用。

远端创建和公开/私有选项分别明确；不自动公开。无 GitHub 远端可先处于草稿/本地准备状态，但不能冒称完整服务器门禁闭环就绪。

预设创建必要的项目 manifest、规则草稿、构建/验收入口和 CI 草稿，不复制平台实现、凭据或全局 AGENTS。普通用户接入已支持技术栈不需要编辑平台源码或手工改运行脚本。

### 9.2 已有项目：识别、提案、不覆盖

选择仓库 → 核对脏状态、规则、工具链/锁文件、远端和 CI → 助手提出适配差异 → 用户审阅 → 通过独立配置变更 PR 安装 → 门禁验证 → 登记。

不自动清理、重置、提交已有改动；不替换项目工具链或重复创建已有 CI。若存在冲突，给出具体对象和安全处理选项。

**必须提供准入引导模式，避免“先接入才能准备接入”的循环：**

- 项目先以“已发现/评估中”登记，默认只能只读诊断、起草和展示适配差异，不能执行普通业务任务。
- 用户批准精确的配置文件差异、范围、受信测试入口及远端动作后，独立 Bootstrap 执行器才在专用 worktree 应用准入变更并创建配置 PR。
- Bootstrap 使用平台已受审的适配能力，不从尚未信任的仓库任意导入代码或执行发现的脚本；实际验证仍处于隔离环境，不开放宿主凭据。
- 现有项目的配置 PR 通过其适用审阅/CI并由人合并；新仓库则先由人确认初始化基线与适用服务器门禁。随后核对规则、验收、远端政策与版本，再转为 READY。
- 状态为“评估中 → 待准入批准 → 配置执行/审阅中 → 验证中 → READY 或 BLOCKED”；中断保留准入动作回执，不通过虚假 READY 放行。

引导动作属于项目登记与配置元数据，不建立一套独立业务任务系统；后续业务任务仍以 GitHub Issue 为准。

### 9.3 首个正式版本的接入预设

| 预设 | 覆盖 |
|---|---|
| 空白/文档 | 文档型任务、适用的格式/链接/内容校验；不虚构单元测试 |
| Python | 识别项目既有 unittest/pytest、静态/类型/构建入口；保留锁定环境 |
| Node/TypeScript | 读取 package scripts、workspace、锁文件和指定包管理器，不互换工具链 |
| Rust/Cargo | workspace、格式、静态、测试、构建及目标平台约束 |
| C++/CMake | presets、配置/构建/CTest、工具链和受控输出 |
| 混合项目 | 将多个已审阅适配器组合为同一任务验收合同 |
| 自定义 | 用户提供并审阅版本化适配合同；不是 Issue 中任意 shell |

以上预设均是首个正式版本的交付范围，不以“以后支持其他语言”替代跨项目要求。未知工具链可以登记为待适配，但不得显示可自动执行。

### 9.4 FishMuse、DevFlow 的定位

- FishMuse：本轮只读发现 pnpm/TypeScript、Cargo/Tauri 和 CMake 相关 manifest。正式接入必须按实际目录规则、Canonical Graph/播放/IPC等高风险合同及真实 CI 适配，不能只跑一套通用 Python 检查。
- DevFlow：本轮只读发现 Python 项目及 pytest/ruff/mypy/build 开发入口。作为待接入业务项目，不把其半成品执行器重新用作本平台底座。
- 两者接入各自单独审阅并验证；本方案不修改它们，标准项目成功也不代表业务项目已接入。

## 10. 项目身份、目录和配置合同

项目登记至少绑定稳定 `project_id`、GitHub host/repository ID、批准的根目录、remote、基准分支、AO 标识、运行器、项目配置修订、模型模板和知识范围。

- 仓库名称不是唯一身份；改名、转移、远端替换或目录迁移需要重新核对。
- 禁止把 HOME、凭据目录或整个 Vault 登记为可写项目。
- 规则来源按当前全局规范、项目和目标目录确认；不能只沿用旧会话文本。
- 会话、运行、worktree、证据、缓存和 AO 指针按 project/run/stage 分区；同项目写入默认串行。
- 核心适配器从可信平台包加载，不能从候选或任意业务仓库动态 import 宿主控制代码。
- 项目 Git 保存可移植的非敏感合同；主机路径、凭据引用和运行映射留在私有登记。

## 11. 跨技术栈验证与隔离合同

### 11.1 平台测试与产品验收分开

平台 CI 测平台实现；业务任务运行自身已审阅的 TestAdapter。不要求每个业务仓库包含 `vendor/starter/tests` 或平台源码。

### 11.2 TestAdapter 最低合同

定义环境探测、依赖/工具链版本、固定命令及参数、工作目录、输入、超时/资源、网络政策、可写输出/缓存、验收来源、结果解析、CI对照与证据格式。

入口来自受审 manifest/适配器，执行时按已批准版本读取；Issue 不提供任意 shell。依赖和锁文件、验收入口、容器/工具链摘要纳入指纹。

### 11.3 基线和冻结验收

按任务类型选择新功能红绿、缺陷复现、行为保持重构、构建/集成等合同。不强制所有任务使用“缺模块”失败。

- 新功能/缺陷应按适用合同证明测试针对目标行为有效。
- 已有要求全部满足时停止无意义变更，不改坏测试制造红灯。
- 冻结测试由控制面注入或只读挂载；Builder 不可改通过条件。
- 合法修改测试本身作为单独受审变更处理，不能与候选自我放行混在一起。

### 11.4 构建与依赖

源代码只读或仅在任务工作区按合同写入；构建目录、临时缓存可受限写入，不放开宿主目录。

依赖下载是独立、明确授权、可核实来源与锁定输入的准备阶段；产品测试默认无外网、无宿主凭据。缓存必须防投毒、按版本命名，并纳入恢复证据。

结果记录命令/参数、退出码、适用测试数量、耗时、环境/工具链、tree、输入与产物摘要。测试数不适用时明确标记，不造出通过数量。

## 12. 任务、有限阶段队列和返工

### 12.1 单任务流程

需求/规格确认 → 结构化任务 → 人类任务批准 → Director/Planner → 必要计划批准 → Builder候选/冻结验证 → 独立Reviewer → draft PR/CI → Knowledge正文 → 人工合并 → 身份/检查核对 → finish/安全同步。

Director 保持建议角色；阶段跳转由 Dispatcher 的确定性合同决定。Planner 的步骤不自动变成可随意执行的命令。

### 12.2 多阶段

助手提出可编辑阶段图，人类确认后创建多个 GitHub Issues。加入有限、确定性的阶段队列：

- 检查依赖合法性、环、同仓库任务身份；
- 依赖完成核对关联 PR 合并、冻结候选、必要 CI与交付记录，不只看 Issue CLOSED；
- 前阶段合并后安全同步 main，再为下一阶段生成新批准材料；
- 不预签未知未来基准；跨仓库依赖必须有明确支持合同，否则阻塞；
- 默认同项目写任务串行，全局消费并发继续受账本限制。

这不是新建通用自治 DAG 引擎；阶段来自明确任务，队列只负责确定性的前置条件和交接。

### 12.3 有界返工

保留候选验证失败后的有限升级；认证、余额、协议、Schema等错误先诊断，不盲目升档。

Reviewer 拒绝后显示人工处理卡；如用户选择“按这些意见返工”，须生成新的受控修复尝试，限定原任务范围和总尝试/预算，任何新候选重新验证、冻结并独立审查。超范围或改规则则新任务/新批准。

不把 `recover` 称为返工；恢复和修改是不同动作。所有旧拒绝和失败证据保持不变。

## 13. Action Broker 与真实人类操作

### 13.1 三主体、双通道

- HumanOperator：通过认证会话审阅关键事项。
- AssistantWorker：读取授权上下文、起草和提出类型化动作。
- ControlPlane：执行身份、策略、状态和预算校验。

助手通道不能访问人类确认端点；人类 Cookie、CSRF token、批准密钥、GitHub/Provider Key 不进入 Worker。

聊天“同意”“继续”“已批准”不会直接签名、合并或接受知识。模型只能打开待审卡，实际授权由独立可信区产生。[S9][S11]

### 13.2 关键操作卡

绑定操作类型、项目/仓库稳定身份、对象、模式、策略/控制包版本、当前输入摘要、操作员、一次性 nonce、有效期、幂等键。

任务附加 base/rules/有效模型快照/预算；计划附加 plan digest；合并附加 head、目标分支最新 baseRefOid、merge-base、预期合并 tree、review binding、CI、方法/noreply；知识附加正文、模板、源版本和目标路径。

流程：服务端读取事实生成卡 → 人类审阅 → 认证/CSRF/Origin/nonce检查 → 再读取并核对事实 → 记录操作意图并消费授权 → 固定原语执行 → 保存回执。

任一关键输入变化使卡失效。签名函数不能裸露成普通 HTTP API。

### 13.3 远端动作与幂等

SQLite 与 GitHub 不能假装是一个原子事务。操作日志区分准备、已提交、核对中、成功、失败。

创建 Issue/PR、合并或派发超时后先查询对象和幂等标识，不盲目重试。不能以模型返回“完成”作为远端动作事实。

## 14. Web、凭据和数据安全

- 本机回环监听，严格 Host/Origin/端口限制；无通配 CORS。
- 本地启动器进行短时一次配对，建立 HttpOnly 会话；状态变更受 CSRF 保护，读取同样认证。
- 会话令牌不进入 URL、localStorage、聊天或日志；不因 localhost 就免认证。
- 安全渲染模型文本、Issue、diff、笔记和附件；禁原始 HTML、脚本和可执行 Markdown。
- 本地静态资源、CSP、禁止外部框架嵌入；可信批准控件不来自模型内容。
- 密钥独立表单处理，配置只保存引用；不回显原 Key，不进入公开 PR/普通导出。
- 同 UID 恶意宿主、管理员或被攻陷控制面不属于当前本机隔离承诺；HMAC不证明所有调用都是人类。[S9][S10][S11]

远程访问、多人/多租户、外网服务或其他设备连接需要单独网络/身份设计与授权，不默认开放端口。未来接入该能力不改变本地安全底线。

## 15. GitHub 门禁、人工合并与收口

项目接入时核验真实仓库规则、所需检查及其来源、可用权限。能力不足时明确阻塞，不能用人工约定或本地绿灯冒充服务器强制门禁。

GitHub原生必需状态检查可能将skipped/neutral视为可接受，并不自动等于本平台要求的“所有适用验证真实成功”。因此必须提供受信的总门禁：明确列出必需子检查，任一缺失、失败、取消或不应跳过的检查未实际运行均拒绝；总门禁本身不得被路径过滤或条件静默跳过，并绑定预期来源。准入和负向验收同时核对本地/工作台判断与服务器实际拒绝效果；仓库无法实施所需服务端政策时保持BLOCKED，不把前端禁用按钮冒充服务器保护。[S13]

界面显示冻结 diff、规格/ADR、独立审查、测试来源、当前 head 与目标分支版本对应的真实 CI、隐私身份和限制。

**目标分支更新同样会影响合并有效性：**合并卡绑定目标分支名、baseRefOid、merge-base及预期合并tree。执行前重新读取head/base/CI；base变化则使旧卡失效，按新基准重新验证并展示，不能仅因head没变继续合并。仓库必须启用并核验“合并前分支保持最新”的严格策略，或具备已审阅的等价服务端合并结果门禁，不能只靠本机预检查。[S13]

最终合并必须由人确认，匹配完整 head并明确 noreply，不使用 admin/auto，不自动删除分支。合并参数能力见 [S12]；本方案明确不启用 merge queue，若未来项目使用队列需独立适配，不把入队当已合并。

合并后核对 mergedAt、合并对象、author/committer、实际parents/tree与已验证合并结果、冻结候选和完整成功检查，再 finish。失败、缺失、取消、跳过不得混称成功；所需检查适用策略必须明确。

GitHub CLI的head匹配参数不是目标base的原子比较交换保证。即使预检查后仍发生外部竞态，也须通过服务端门禁及合并结果复核识别；若实际结果偏离批准，不自动finish、重试或撤回已发生的合并，转入异常核对。需要更强原子保证的项目必须有对应受审服务端能力，缺失时明确阻塞，不声称本机锁能阻止外部写入。

同步 main 前检查工作区/分支归属，使用安全快进；存在用户改动或分叉则停止，不 reset/clean。Issue自动关闭与工作流DONE分别查询，不手工关Issue绕依赖。

## 16. 知识检索、pending 与人类接受

Knowledge 仍是独立模型角色，只获得脱敏证据，不能写 Vault。交互助手可通过授权检索获得相关笔记的最小片段和来源，不能全库上传。

工作台提供相关笔记搜索、重复候选对比、事实/推断核对、隐私审核。没有实际查询结果时不得显示“已完成查重”。

Draft Writer 继续只按 AI-Knowledge-Draft 模板新建 `00-Inbox/AI-Drafts/` 下的 pending，不覆盖、接受或搬移。

人类逐篇接受在独立审核服务完成：展示完整正文与来源、确认源版本、目标位置和精确状态变化。只有本人直接确认可触发；Assistant/Knowledge/Writer都没有该能力。

既有accepted笔记默认只读，修改/删除/移动须具体授权。无价值内容可跳过；测试笔记明确标测试，不能当作正式知识。

## 17. 预算与认证通道

本轮已授权 API 总上限仍为 **1 USD，付费并发 1**。新助手、项目、后台 SDK 请求、重试和恢复都共用原账本，不创建新免费额度。

付费请求先按完整可核实合同预留，已知usage保守结算，未知用量占满预留。没有最终账单证据时 actual_cost 保持未知，而不是 0。

模型费率、上下文、输出和额外计费项未知、过期或未适配时阻止付费派发。配置保存和无消费诊断不自动做真实调用。

ChatGPT 登录通道的配额按原服务另行处理，不伪称为 DeepSeek 费用或无限免费。工作台不主动切换认证。

未来消费授权通过独立人类政策变更执行；当前上限在界面锁定，不能点一次普通按钮加预算。更高模型等级不扩大预算或权限。

## 18. 长期运行、恢复与运维

### 18.1 后台服务

用户级启动器/服务管理平台与其受管进程；桌面入口打开工作台，不依赖某个练习库终端常驻。安装自启或服务配置需在实施时确认。

浏览器关闭不杀任务；重连通过事件 cursor/查询恢复视图，不调用 run 或模型。作业的PID/starttime、归属、租约续租、超时、取消和退出状态可核对。

“停止助手回复”“停止接单”“取消指定运行”“停止AO”“关闭平台”分别表达影响范围；取消已发API请求不承诺退款。

### 18.2 恢复

启动/重启先协调存活进程、检查点、AO和远端事实，不自动重复付费。阶段缓存绑定相同输入与配置，规则/候选变化不复用。

UI断开、双击、多标签和错误重试仅对应同一动作回执。无法确认远端写入时保持核对中，不宣称成功或再次执行。

### 18.3 备份恢复

备份采用一致性SQLite备份，包含版本配置、账本、授权/动作日志、必要检查点；不运行中只复制主db而丢WAL。

凭据独立由用户安全处理；不复制整个HOME、Vault或所有项目源码。恢复后默认核对模式，不重放旧批准、合并或模型请求。

恢复不得让已发生费用下降。最新账本/用量完整性无法确认时，禁止新付费请求，先保守协调。

### 18.4 升级与回滚

固定发行、依赖和适配器版本/哈希；升级预览兼容性、配置与DB迁移，先备份、排空或保留受支持旧环境。

AO现有兼容补丁按项目/版本合同隔离，不静默套新版本。升级需重新验证冷启动、空闲派发、恢复和Harness。

软件回滚不撤销GitHub事实、不倒退费用、不覆盖旧证据。项目移除默认只解除登记，不删除代码、worktree、分支、Vault或日志。

## 19. 版本与接口演进

平台包、项目manifest、Profile、动作卡、TestAdapter、证据格式和数据库分别有schema版本与兼容范围。

旧练习库记录按原版本只读展示，不批量改写为新协议。迁移有来源、校验和、回滚说明；不自动复活旧批准。

### B. 助手与模型配置

- B01 WorkbenchAssistant能澄清、起草、发布预览、查询状态和解释证据，不依赖当前聊天窗口。
